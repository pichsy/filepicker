# 图片裁剪功能设计方案（讨论稿，未开始编码）

> 目标：做微信那种裁剪体验，结合本库（`com.gitee.pichs:filepicker`）现状落地。
> 本文只写方案，不含代码。等这 5 个问题拍板后再出详细设计文档。

## 一、需求认知（已与需求方对齐）

微信里有两类裁剪，交互和约束完全不同，不能混成一个需求：

| 场景 | 入口 | 作用于 | 裁剪框 |
|---|---|---|---|
| **聊天 / 朋友圈** | 预览大图页面的「编辑」按钮 | **当前正在预览的那一张**（多选时也只编辑这一张） | 自由比例 + 比例预设，可拖角改大小 |
| **头像** | 单选模式下**点图片直接进入** | 点的那一张 | **1:1 固定框**，只能拖动/缩放图片 |

两者共用同一套内核，只是配置不同 —— 这是"先做一个、再做另一个"的基础。

## 二、共用内核

| 组件 | 职责 | 可测性 |
|---|---|---|
| `CropGeometry` | 纯 Kotlin 数学：屏幕坐标 ↔ 原图像素坐标映射、边界钳制（不能露黑边）、比例锁定、旋转/镜像换算、最小裁剪尺寸 | **纯函数，可写单测**（和 `SelectRulesEngine` 一样的做法） |
| `CropImageView` | 自绘 View：图片 Matrix（平移/缩放）+ 裁剪框 + 半透明遮罩 + 三分线 + 四角括号 + 拖角把手；手势用 `ScaleGestureDetector` + `GestureDetector` + 角点 hit-test 分层 | 需真机验收 |
| `CropEngine` | 显示解码（`inSampleSize` 到屏幕，绝不解原图）、输出解码（`BitmapRegionDecoder` **只解裁剪区域** + 采样）、旋转烘焙、EXIF 归一化、JPEG q90 写文件 | 可单测采样尺寸计算 |
| `FilePickerCropActivity` | 全屏裁剪页（**建议 Activity，不用 PopupWindow**：避免和预览页的 ViewPager2/拖拽手势抢事件，返回栈也干净） | 设备验收 |
| `CropConfig` / `CropUIConfig` | 外部配置：比例、输出最长边、质量、是否显示网格/圆形参考线、文案颜色 | — |

**关键原则（沿用库现有风格）**

* 默认关闭，`Builder` 显式开启才生效（和 7.4.0「规则表非空才启用新模型」一致，升级不改变已有行为）；
* 新能力 = 新 API + 新版本号（minor），不改老 API 语义；
* **非破坏**：编辑结果只写 `cacheDir/filepicker/edit/` 的临时文件，
  **绝不修改/覆盖相册原图**；选中项身份仍是原图实体，编辑只是会话级覆盖
  （详见 `docs/image-editor-plan.md` 第二节）；
* 回调给宿主的仍是原图实体，新增只读字段 `editedPath`（非空 = 已编辑，上传用这个）；
  失败/取消 → 回原图，不阻塞确认流程。

## 三、方案 B（建议先做）：头像 / 单选 1:1 裁剪

### 交互

```
点格子（单选模式）
  → 直接打开裁剪页（黑底）
  → 1:1 固定白框（大小固定、不可拖角），图片可拖动 + 双指缩放
  → 图片始终盖满框（露黑边会被自动弹回）
  → 可选圆形参考线（头像最终是圆的，给用户预览感）
  → 底部：取消 / 完成
  → 完成后自动作为唯一选中项并 finish，回传给宿主
```

### 接入点（结合现有代码）

| 项 | 改哪里 |
|---|---|
| 开关 | `FilePicker.Builder` 新增 `setAvatarCropAspectRatio(CropAspect.SQUARE)`（或 `setAvatarCropEnable(true)`） |
| 入口 | `FilePickerFragment` 里格子的点击回调：单选 + 裁剪开启时，不执行"选中"，直接启动 `FilePickerCropActivity` |
| 单选判断 | 已有 `FilePickerViewModel.isCanSingleClickSelect()`（容量=1 且 `singleClickEnable`），直接复用这个判定 |
| 回传 | 裁剪结果包装成 `MediaEntity` → 走原有 `FilePickerCallback`；不新增回调接口 |
| 配置 | `FilePickerUIConfig` 加几个字段（是否显示网格、圆形参考线、按钮文案/颜色） |

### 数据流

```
currentFolderDataList[index]（原图实体，身份不变）
  → CropActivity(原图 uri, 配置)
  → CropEngine 输出 previewFile（屏幕级，立即）+ editedFile（原图级，后台）
  → 选中"原图实体"，并把 EditSession 挂到它上面（会话级覆盖）
  → finish；回调里 entity.editedPath = 裁剪结果文件，相册原图未被修改
  → 本次选择内该图的网格缩略图一直是裁剪后的样子，左下角带 25dp 已编辑角标
```

### 复杂度评估

* 手势：只有**平移 + 缩放**（无拖角），约束就是"图必须盖满框"；
* 无比例切换、无旋转/镜像（P1 可不做）、无"编辑后撤销"；
* 回传链路短，不需要改预览页/底条/选中序号任何逻辑；
* **工作量 ≈ 1 天**（内核 0.6 天 + 裁剪页 0.3 天 + 接入 0.1 天），验收 1 个用例就能过。

## 四、方案 A（后做）：预览页「编辑」裁剪（聊天 / 朋友圈）

### 交互

```
预览大图页（底部条上方 / 工具栏右上）新增「编辑」
  → 只对当前页那张图生效（视频、GIF 禁用或隐藏）
  → 打开裁剪页：自由框（8 个把手：4 角 + 4 边中点）+ 旋转 90° + 还原；**没有比例预设**（微信 8.0.74 实测）
  → 完成 → 回到预览页：**当前这张显示裁剪后的图，但只是会话级临时覆盖**
    （相册原图不动、选中项还是原图实体、选中顺序/计数全不变）
  → 网格/底条里这张图显示"编辑后"的缩略图，并在**左下角显示 25dp 已编辑角标**
  → 再点"确定/发送"，宿主拿到原图实体 + editedPath（编辑产物路径）
```

### 接入点

| 项 | 改哪里 |
|---|---|
| 入口按钮 | `FilePickerPreviewDialog`：底部栏左侧加「编辑」（或工具栏右侧）；受 `isShowEditEntry` 控制 |
| 当前图片 | 已有 `mCurrentItem` + `viewModel.getCurrentFolderDataByPosition(...)`，直接取 |
| 裁剪页 | 复用方案 B 的 `FilePickerCropActivity`，仅配置不同（自由框 8 把手、旋转、还原；无比例列表） |
| **编辑覆盖** | `FilePickerViewModel` 新增 `editSessions: Map<原图path, EditSession>`；**不替换实体**，只挂会话。选中顺序、计数、规则引擎全部天然不变 |
| 显示统一 | 三处（网格缩略图 / 预览大图 / 底部条）都走 `editSessions[entity.path]?.previewFile ?: 原图`，自动一致 |
| 预览刷新 | `viewPager2.adapter.notifyItemChanged(index)`（只刷这一页）+ 底条按 `revision` 重绑 + `refreshStripSelection()` + `updateIndexUI()` |
| 回传 | `FilePickerCallback.onResult` 返回原图实体，`entity.editedPath` 指向编辑产物；可选 `onResultWithEdit` 拿会话参数 |
| 已编辑角标 | 网格/底条格子左下角显示 `filepicker_ic_image_edited.png`，25dp（已放入 `drawable-xxxhdpi`），受 `entity.isEdited` 控制，可配尺寸/图标/显隐 |

### 数据流（最关键的一段）

```
预览页 mCurrentItem（原图实体，身份不变）
  → CropActivity（自由裁剪 / 旋转 / 还原）
  → previewFile（屏幕级，立即）+ editedFile（原图级，后台）
  → viewModel.editSessions[原图path] = EditSession(...)   ← 只挂覆盖，不动实体
  → 三处显示按覆盖查找：网格 / 预览大图 / 底条全部变成编辑后的图
  → 选中顺序、计数、规则校验、绿框位置全都不变
  → 相册原图零改动
```

**这就是"选中还是原图、预览显示编辑后、相册原图不变"的实现方式。**

### 复杂度评估

* 手势：框移动 + 拖 8 个把手改大小 + 旋转后框宽高交换（`CropGeometry` 里都有对应纯函数）；
* 状态：编辑只改**一张**；因为采用"会话覆盖"而非替换实体，选中序号/底条位置/绿框/计数/规则校验
  **天然不变**，只需保证三处显示都走同一个覆盖查找 + 刷新时机正确；
* **工作量 ≈ 2~3 天**（内核扩 0.5~1 天 + 数据替换 0.5 天 + 预览页接入 0.5 天 + 验收 0.5 天）。

## 五、两种方案对比：先做哪个？

| 维度 | 方案 B（头像 1:1） | 方案 A（预览「编辑」） |
|---|---|---|
| 依赖内核 | 平移+缩放，固定框 | 平移+缩放+拖角+比例+旋转 |
| 改动面 | 1 个入口 + 结果回传 | 预览页 UI + ViewModel 数据替换 + 3 个列表同步 |
| 状态风险 | 低（单选，无多图） | **中高**（替换当前项后选中/底条/计数一致性） |
| 验收成本 | 1 个用例 | 6~8 个用例 |
| 对用户价值 | 头像场景直接可用 | 聊天/朋友圈核心体验 |

**结论：先做 B。** 原因不是 B 更有价值，而是 **B 的需求是 A 的严格子集**：

1. B 先把内核（`CropGeometry` + `CropImageView` 固定框 + `CropEngine` 解码/输出）做出来并验证，
   A 只需要在内核上加"拖角 + 比例 + 旋转"；
2. B 的入口/回传最简，能最快出一个**可验收、可发布**的 7.5.0；
3. A 最难的是"替换当前预览项"的数据一致性，这块可以单独设计、单独测，不被内核问题干扰。

## 六、里程碑建议

| 版本 | 内容 |

## 七、需要拍板的 5 件事

1. **结果形式**：生成临时文件（**已定**）；本次选择内列表展示被编辑后图替换，磁盘原图不动；
   取消选择/重新选择都不回退；是否需要"还原原图"入口？
2. **头像裁剪**：要不要圆形参考线？输出要**方图**还是**带透明圆的 PNG**？
3. **「编辑」按钮位置**：预览页底部左侧（更接近微信）还是工具栏右上（改动最小）？
4. **视频/GIF** 在「编辑」入口下：隐藏、置灰还是 Toast 提示不支持？
5. **默认开关**：裁剪功能默认关闭、显式开启（推荐，语义同 7.4.0 规则模型）——确认？
